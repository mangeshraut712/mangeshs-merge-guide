# Reproduction and final validation

1. Reproduce the reported behavior against a recorded base revision. Separate observed failure, expected contract, and root-cause hypothesis. Trace real consumer wiring and existing helpers. Compare the reported failing invocation with the actual CI commands and record any gap in entry-point coverage. Distinguish a supported upstream defect from a local setup failure or already-fixed release.
2. For a behavioral code fix, design regression evidence that observes the promised behavior, not merely an implementation detail. Follow the repository’s test policy: use its supported harness and, where a committed test suite is disallowed, a permitted reproduction or validation instead. Do not force test infrastructure onto a bounded docs or data fix. Run the same behavioral check against the unfixed base and fixed tree. Verify it fails for the intended reason before the fix, then passes after it. If practical, revert only the fix or use a targeted mutation to check that the assertion detects the defect. Preserve the working tree and user changes.
3. Preflight the intended runtime or tool executable and version; a command name alone does not establish toolchain identity. Verify the executed or imported code comes from the intended checkout, not a stale installed release. If red/green execution is blocked, label it unverified and describe the exact missing dependency or environment. Do not turn a plausible test or green-only run into proven regression coverage.
4. Validate the actual contract rather than a convenient proxy: visibility rather than mounted text, authenticated versus logged-out flows when relevant, real supported platforms rather than a renamed fixture, and actual consumer/API behavior rather than disconnected helper tests. When a change promises callback or event side effects, assert those effects as well as visible state. Do not claim first-hand account testing you could not perform. Measure added per-item/network work where relevant. Preserve authentication, authorization, replay protection, resource bounds, and data integrity; stop or narrow a design that weakens them. Use supported security reporting instead of publicly exposing sensitive vulnerability details.
5. Keep the patch aligned with project conventions and feedback, including compatibility, ownership, naming, docs, changelog, and release notes when required. Avoid unrelated refactors, speculative hardening, and duplicate fixes.
6. Run relevant tests, lint, type checks, formatting, and required aggregate checks against the final revision. Record commands, outcomes, scope, and head SHA. Distinguish pass, fail, blocked, not run, skipped, neutral, and pending. Green focused tests do not imply full CI success.
7. Before each push, check what you are about to publish:
   - The commits carry the contributor's real identity: `git log --format='%an <%ae>' BASE..HEAD` shows the name and an email linked to their GitHub account, not a placeholder or a machine default. Projects with a CLA or deployment previews often block commits from an unknown email.
   - Every commit has a sign-off (`git commit -s`) when the project requires a DCO.
   - `git diff --stat BASE..HEAD` lists only intended files, with no lockfile churn, generated output or local config.
   - While a PR is under review, add new commits rather than force-pushing, so reviewers can see what changed since they last looked. Rewrite history only when the project asks for it or before anyone has reviewed. Never force-push to a branch someone else is also pushing to.
8. Review the diff independently when warranted or required. Distinguish author claims, CI results, bot/AI-assisted reviews, verified maintainer direction, and independently reproduced evidence. A non-author account is not automatically human or a maintainer. Do not present automated review as maintainer approval. Verify remote checks and review disposition on the latest head; an earlier pass does not certify later changes. Do not claim readiness with unanswered blocking feedback, required checks missing, or policy gates unresolved.


## When local validation is blocked

After diagnosing the local blocker, record the checks that ran and the checks that still need the supported environment. When a draft PR is authorized and repository policy allows it, use hosted CI to finish verification. Record the tested head and check links. Move the PR out of draft only after the applicable checks pass and the diff is ready for review. Follow the repository’s ordinary review and merge rules.

For example, a dependency patch can pass lint and the lockfile audit while a local engine download stalls. A draft can exercise the supported CI job for installation, generation, build, and tests. If the job requires maintainer authorization, report that gate and keep the missing results pending. If CI passes on the same head, record the hosted results and the remaining review decision.

## Read a hosted CI receipt

When a PR has no check rollup, inspect the snapshot's `sections.workflow_runs`. It contains upstream repository runs filtered by the sampled head SHA. Match the event and PR before attributing a run; two branches can point to the same commit. A run with `action_required` needs an upstream decision. Report its URL, the head and the next owner. An empty array means the search returned no runs for that SHA; PR merge-ref workflows or external CI may still exist. If the section is absent, check `errors` and the collector version.

For a first contribution, ask “What can I verify locally on this PR?” Pick the changed behavior, run its focused test, then the project-prescribed suite. Report the runner, revision, passed and skipped counts, plus any hosted scenario left to exercise. A contributor with release experience can also compare the head with the last validated revision: changes to a dependency lockfile, package version or runner image may require a new consumer test even when the workflow file is identical.
